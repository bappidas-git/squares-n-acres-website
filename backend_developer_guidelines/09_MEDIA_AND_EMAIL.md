## How uploads work

**The API never receives a file** (D12). The admin's media library, the
property photo gallery and the public careers form upload from the browser
straight to Cloudinary with an **unsigned upload preset**, and the API stores
what Cloudinary answered — an address and its details — as JSON:

- The cloud name and the preset are
  `siteSettings.integrations.cloudinaryCloudName` and `.cloudinaryUploadPreset`,
  which the client fills in under Settings → Integrations, and which win over
  the build's `REACT_APP_CLOUDINARY_CLOUD_NAME` / `…_UPLOAD_PRESET`. With either
  missing, the upload zone is replaced by "Add by URL" and everything else keeps
  working.
- The library asks Cloudinary for the folder `sna/<folder>` —
  `sna/properties/lakeview-heights` for a listing's photographs — and stores
  `<folder>` on the record (`05_BUSINESS_RULES.md` → "Media library"). "Test
  uploads" in the same settings tab sends a one-pixel picture to
  `sna/_diagnostics` and stores nothing. The careers form uploads to
  `resumes/`.
- The browser enforces the limits, because it is the only place that sees the
  file: images (jpg, jpeg, png, webp, avif, gif) and documents (pdf, doc, docx)
  up to 10 MB, videos (mp4, webm) up to 100 MB, résumés (pdf, doc, docx) up to
  5 MB.
- `POST /admin/media` files the record; the grid, the picker and every form read
  the address from it. Nothing in the API talks to Cloudinary today, and nothing
  needs to for v1.

## The upload preset

The preset's name and the cloud name ship inside the site's JavaScript — an
unsigned preset is public by design. What a stranger can do with it is
whatever the preset allows, so lock it down in the Cloudinary console
(Settings → Upload → Upload presets):

| Setting | Value | Why |
| --- | --- | --- |
| Signing mode | **Unsigned** | the browser has no secret to sign with; a signed preset refuses every upload |
| Folder | **empty** | the admin files every upload under `sna/<folder>` itself. For an unsigned upload a folder set on the preset *replaces* the one the request names — Cloudinary applies the preset's value over the request's — so `sna` there would drop every file into one flat folder |
| Allowed formats | `jpg, jpeg, png, webp, avif, gif, mp4, webm, pdf, doc, docx` | anything else is refused at Cloudinary, whoever sends it |
| Use filename | off (the default) | every upload gets a random public id, so two `villa.jpg` never collide |
| Overwrite | nothing to set | Cloudinary never overwrites on an unsigned upload, whatever the preset says |

Two things a preset **cannot** do, and what covers them:

- **Cap the file size.** Cloudinary's presets have no per-preset size limit; the
  browser's checks above are the site's, and the plan's own maximum file size is
  the only ceiling Cloudinary applies. Somebody calling Cloudinary's API by hand
  skips the browser.
- **Confine uploads to a prefix.** A preset can pin one folder (the flat-folder
  trade-off above), not a subtree. If confinement matters more than the tree to
  the client, set the folder to `sna`: the library keeps its own folders — they
  live on its records — and Cloudinary's console shows one folder.

The real lock is **signed uploads**, when the client wants it: an admin-only
endpoint on the API signs the upload parameters with the API secret (held in
`.env`, never in the settings or the bundle), the library asks it before each
upload, and the preset switches to signed. It is not in the registry; add it
there first, like every endpoint.

## The careers form

**Today** the public careers form uploads with the same site-wide preset as the
admin, into `resumes/`. Flag this to the client, because it means:

- every visitor holds the preset the admin uses, so the careers page is a
  one-click way to put images and videos — not only résumés — on the client's
  account (anyone who reads the bundle could already; the form makes it easy);
- a résumé is **personal data** on a public delivery address: whoever holds the
  URL can read it. The addresses appear only in the admin, but they are not
  secret.

**The recommended set-up** is a second unsigned preset for the careers form
alone: folder pinned to `careers` (here pinning is right — the form never
chooses a folder), allowed formats `pdf, doc, docx`, and nothing else allowed.
The frontend reads one preset today; using a second needs a setting beside the
first (`integrations.cloudinaryResumePreset`, falling back to the site-wide one)
read by the careers form — a small change to make with the client's agreement,
and to add to the settings schema in the same commit.

**Retention.** Agree a period with the client — twelve months after the opening
closes is common — and enforce it on the server: a scheduled command that
deletes the application and its Cloudinary asset together (Cloudinary's Admin
API with the API secret; a PDF is an `image` resource, a Word file a `raw` one).
Under India's Digital Personal Data Protection Act an applicant may ask for
their data to be erased; the same command, for one application, answers them.
For stronger privacy the résumé preset can deliver `authenticated` assets, and
`GET /admin/job-applications/:id` then answers a short-lived signed address —
again a server-side change, since signing needs the secret.

## Deleting and orphans

**Deleting a library record never deletes the Cloudinary asset** — by design
(D12): the API has never held the file, the browser has no secret to delete
with, and an address that was ever published may still be in an e-mail, a
cached page or a search engine's image index. A single delete, `?force=true`
and the bulk delete all remove the record only, and the admin says so.

So assets outlive their records ("orphans"). The options, in the order to
consider them:

1. **Leave them.** Storage is cheap and nothing breaks; this is the default.
2. **Clean by hand** in the Cloudinary console: search `sna/` for assets whose
   address no record holds. `sna/_diagnostics` holds only "Test uploads"
   pictures and can be emptied at any time.
3. **A scheduled command** on the API: list the assets under `sna/` (and
   `careers/` or `resumes/`) with the Admin API, subtract every address the
   records use — the same search as a delete's `usedIn`
   (`05_BUSINESS_RULES.md` → "Media library") plus `media.url` — and delete
   what is left **and older than 30 days**. Run it dry first and have it report
   what it would delete before it ever does.

## Folders

Folders are the library's filing, not Cloudinary's. **Renaming a folder
(`POST /admin/media/folders/rename`) or moving files (`POST /admin/media/bulk`
with `move`) changes the library's records only**: `url` and `public_id` stay,
the Cloudinary asset keeps the path it was uploaded to, and nothing that points
at it breaks. Uploads made after a rename go to the new path, so over time
Cloudinary's tree and the library's differ — expected, and harmless, because
nothing reads Cloudinary's folders. Do not "fix" it by renaming on Cloudinary:
that changes the public id, and with it every address the site has published.

## Lead notification e-mail

The mock logs a new lead and sends nothing. Laravel sends the alert:

- **Trigger:** a lead **stored** by `POST /leads` (the public forms) or
  `POST /admin/leads` (the desk). Not an update, not a lead the honeypot
  swallowed, not a 422 or a 429 — and a repeat enquiry is a new lead, so it
  notifies like any other.
- **Recipients:** `siteSettings.leads.notificationEmails` — the list under
  Settings → Lead notifications, admin-only (the public `GET /settings` omits `leads`). An
  empty list sends nothing; the lead is stored all the same.
- **From:** `MAIL_FROM_ADDRESS` on the site's own domain, `MAIL_FROM_NAME` the
  site name. **Reply-To:** the lead's e-mail when it gave one, so "Reply" answers
  the enquirer.
- **Subject:** `New enquiry — <listing title, or the source's label> — <name>`.
- **Content:** name, phone (as a `tel:` link), e-mail, the source's label, the
  listing's title and its public address (`<siteUrl>/properties/<slug>`), the
  message, the requirement when sent (type, budget, timeline), who the lead was
  assigned to (after step 6 of `POST /leads`, so the alert names the owner),
  `pageUrl`, the UTM fields, the time in IST, and a link to the lead in the
  admin — `<siteUrl>/admin/leads/<id>`. Plain text and HTML; escape everything
  the visitor typed.
- **Failure:** a queued mailable (`ShouldQueue`) with `tries = 3` and a backoff
  of 60 seconds; after the third failure it is logged (the `failed_jobs` table
  and the log channel) and nothing else happens. **The e-mail never fails the
  lead:** the 201 is answered whether the mail goes, waits or fails — with
  `QUEUE_CONNECTION=sync`, catch and log the mailer's exception rather than let
  it reach the response.

## The test alert

`POST /admin/settings/test-lead-alert` — admin only, no body — sends a test
alert to the **saved** `leads.notificationEmails` (not what the form holds
unsaved, which is why the button asks for a save first):

```
200 { "data": { "sentTo": ["info@squaresnacres.com"], "sentAt": "2026-01-15T09:30:00.000Z" },
      "message": "Test alert sent to 1 address." }
422 { "message": "The given data was invalid.",
      "errors": { "leads.notificationEmails": ["Add at least one notification e-mail and save the settings first."] } }
502 { "message": "<the mailer's reason>" }
```

Send it **synchronously** — the admin is waiting for the answer, and the point
of the button is an honest one: 200 only once the relay accepted the message,
502 with the relay's own words when it refused (authentication, a blocked port,
an unverified sender). Subject `Test lead alert — <site name>`; the body says it
is a test and lists what a real alert contains. The mock logs it to its console.

## Sending mail from Cloudways

Cloudways servers send no mail of their own worth trusting; use an SMTP
provider. Any of these works with Laravel's stock `smtp` mailer and needs no
package:

- **The platform's SMTP add-on**, set up in the server's settings — the
  quickest, with the platform's sending limits.
- **Amazon SES** (region `ap-south-1`, Mumbai): SMTP credentials from the SES
  console, host `email-smtp.ap-south-1.amazonaws.com`.
- **Mailgun**, **SendGrid**, **Postmark** or Google Workspace's relay: the
  provider's SMTP host and credentials.

```dotenv
MAIL_MAILER=smtp
MAIL_HOST=<the provider's SMTP host>
MAIL_PORT=587
MAIL_USERNAME=<…>
MAIL_PASSWORD=<…>
MAIL_FROM_ADDRESS=no-reply@squaresnacres.com
MAIL_FROM_NAME="Squares N Acres"
```

- Port **587** (STARTTLS) or 465 — many clouds block 25 outright.
- Publish the provider's **SPF** and **DKIM** records for the sending domain and
  a **DMARC** policy, or the alerts land in spam — which reads to the desk as
  "no leads today".
- **Staging** must not e-mail the desk: `MAIL_MAILER=log`, or a catcher such as
  Mailtrap. The full smoke walk and the Postman collection post enquiries.
- Prove it before launch with the test alert, then with one real enquiry
  (go-live checklist of `07_DEPLOYMENT.md`).

## The WhatsApp template

`siteSettings.leads.whatsappTemplate` (a string, at most 500 characters) is the
message the desk's WhatsApp buttons open with. The API only stores it —
nothing is sent server-side; the browser opens `https://wa.me/<digits>?text=…`
with the template filled in. Its placeholders:

| Placeholder | Becomes |
| --- | --- |
| `{name}` | the lead's name |
| `{property}` | the listing they asked about (its stored title when the listing is gone) |
| `{agent}` | the colleague the lead is assigned to |
| `{link}` | the listing's address on the site |
| `{brand}` | the site name from Site settings |

A placeholder with nothing behind it is dropped with the space before it
("Hello {name}, about {property}." reads "Hello Asha, about." for a lead with no
listing); any other `{…}` is left as typed. The default is "Hello {name}, this
is {brand} following up on your enquiry." Validate it as a string of at most 500
characters; do not interpret it.

## reCAPTCHA (planned addition)

The site key is stored today (`siteSettings.integrations.recaptchaSiteKey`) and
only decides whether the forms show the reCAPTCHA notice; **no token is sent and
nothing is verified**. The honeypot and the ten-a-minute throttle are what
defend the forms (`01_API_CONTRACT.md` → "Rate limiting"). When it is wired:

- The public writes — `POST /leads`, `POST /newsletter/subscribe`,
  `POST /jobs/:id/apply` — gain an optional `recaptchaToken` (reCAPTCHA v3, one
  action per form: `lead`, `newsletter`, `apply`).
- The API verifies it with `POST https://www.google.com/recaptcha/api/siteverify`
  (`secret`, `response`, `remoteip`) using `RECAPTCHA_SECRET_KEY` from `.env` —
  never from the settings, which the admin reads back.
- It accepts `success: true`, the expected `action`, a `hostname` of the site's
  and a `score` of at least `RECAPTCHA_MIN_SCORE` (0.5 to start). Anything else
  is **422 on `recaptchaToken`** with "Please try again." — a person can; a
  script learns nothing new.
- With no secret configured, verification is skipped: development, the mock and
  a staging copy keep working, and so do the smoke test and the Postman
  collection.
- The honeypot and the throttle stay. Add the field to the three bodies in
  `src/services/schemas/` and the registry in the same change.

## Password reset (planned addition)

Today an administrator resets a password from Settings → Users, and the sign-in
page says so. The self-service pair, when it is built:

```
POST /auth/forgot  { "email": "…" }
  200 { "data": null, "message": "If that address has an account, a reset link is on its way." }

POST /auth/reset   { "email": "…", "token": "…", "password": "…", "passwordConfirmation": "…" }
  200 { "data": null, "message": "Password changed. Sign in with the new one." }
  422 on token     — unknown, used or older than 60 minutes
  422 on password  — the rule of every password: 8 characters, a letter and a digit
```

- `forgot` answers the **same 200 whatever the address** — an unknown or
  inactive account gets no e-mail and no different answer, so the endpoint
  cannot be used to find accounts. Throttle it: 5 an hour per IP and address.
- The e-mail links to `<siteUrl>/admin/reset-password?token=<token>&email=<email>`
  (a screen the frontend adds with the endpoints) and says the link lasts an
  hour.
- A successful reset deletes the token, **revokes every token of the account**
  (every session signs out, as a password change does) and writes nothing else.
- The tokens live in Laravel's own table, stored hashed — never the token
  itself:

```sql
CREATE TABLE password_reset_tokens (
  email      VARCHAR(191) NOT NULL PRIMARY KEY,  -- one live token per account
  token      VARCHAR(255) NOT NULL,              -- a hash of the token sent
  created_at TIMESTAMP NULL                      -- the hour is counted from here
);
```

Laravel's password broker implements all of this; wire it to these two routes
and this envelope, and add both entries to the registry first.
